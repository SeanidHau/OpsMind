# 第 73 阶段：GPUI 用户输入续跑

本阶段在桌面端接入等待用户输入的恢复流程。当实时诊断以 `waiting_user_input` 状态结束时，界面显示后端返回的待回答问题，并提供补充信息输入区。

## 运行流程

1. 桌面端接收 `run_finished` 事件。
2. 只有状态为 `waiting_user_input`，且 `run_id` 为 UUID 格式、待回答问题非空且不超过 2000 个字符时，界面进入等待输入状态。
3. 操作人员填写补充信息并选择“提交并继续”。
4. 桌面端在后台调用 `POST /api/v1/runs/{run_id}/input`。
5. 前台线程接收安全运行摘要，并更新运行状态。

桌面端不创建新的运行。恢复请求使用后端返回的原始 `run_id`。

## 数据与界面边界

桌面端只显示待回答问题、受控运行状态和步骤数。接口返回的最终回答与错误列表不会进入本阶段的界面。

补充信息为空或超过 4000 个字符时，桌面端不发起请求。运行 ID 不符合 UUID 格式时，桌面端不构造恢复请求路径。

恢复请求在后台执行器中完成。GPUI 前台线程只处理状态更新和重绘，不执行阻塞 HTTP I/O。

## 审批边界

本阶段不提供高风险动作审批按钮。当前运行摘要没有可展示的安全审批对象；桌面端不会根据内部动作或轨迹字段推断审批内容。后续阶段需要先定义审批摘要契约，再接入审批决议和续跑操作。

## 验证范围

Rust 测试覆盖恢复请求的 HTTP 路径与载荷、待回答问题长度限制和运行 ID 格式限制。完整验收还包括 Rust 编译检查，以及 Python 服务端的测试、静态检查和类型检查。
